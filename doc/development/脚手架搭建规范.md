# Zephyr 标准化项目脚手架搭建规范

**文档编号**: ENV-FW-STD-001
**适用范围**: EnerVenue BMS 固件项目(基于 Zephyr RTOS,面向 ISO 26262 / IEC 61508 功能安全认证)
**版本**: v1.0
**状态**: 草案

---

## 1. 目的

统一团队内 Zephyr 项目的初始化方式、目录结构、依赖版本管理和配置分层策略,确保:

- 任意成员在任意时间用同一份 manifest 都能拉出**完全一致**的构建环境(可复现构建,ISO 26262 对配置管理的基本要求)
- 新项目/新板卡接入时有统一模板可循,不依赖口口相传
- 为后续 MISRA C:2012 合规扫描、Twister 自动化测试、代码评审流程预留标准挂载点

本规范不覆盖具体外设驱动编写规范、编码规范(MISRA 细则另行成文),仅覆盖**工程脚手架层面**的约定。

---

## 2. Workspace 拓扑选型

统一采用 **T3 拓扑(forest,专用独立 manifest 仓库)**:一个只含 `west.yml` 的独立 manifest 仓库,统一管理 zephyr、各模块与应用仓库(均作为 project 登记)。禁止 T1(zephyr 仓库兼作 manifest)与 T2(应用仓库兼作 manifest)。

> **术语澄清(勿混淆)**:west 官方三拓扑中——T1 = zephyr 仓库即 manifest 仓库;**T2 = 应用仓库自身即 manifest 仓库**(如官方 `example-application`,`west.yml` 就在 app 仓库内);**T3 = 独立专用 manifest 仓库**(与 zephyr、app 均分离)。因此"独立 manifest 仓库"是 T3 的定义,不是 T2。

选 T3 而非社区单应用最常用的 T2,理由:

- manifest 仓库独立,版本锁定、变更评审可单独走流程,不与应用代码耦合
- 应用代码与 zephyr 版本解耦,升级 zephyr 版本时只改 manifest,不用动应用代码结构
- 面向多产品线 / 多应用共享同一份 zephyr 与模块版本锁定的演进(单应用阶段亦兼容)

```text
<workspace-root>/                    # west init 执行所在目录,自由命名
├── .west/                           # west 自动生成,不纳入版本管理
├── <project>-manifest/              # manifest 仓库(GitHub)
│   └── west.yml
├── zephyr/                          # west update 拉取,不纳入版本管理
├── modules/                         # west update 拉取(hal_stm32等),不纳入版本管理
└── <project>-app/                   # 应用仓库(GitHub),独立版本管理
```

`.west/`、`zephyr/`、`modules/` 均加入顶层 `.gitignore`(如果 workspace 根目录本身被纳管的话;正常情况下 workspace 根目录不建仓库,只有 manifest 仓库和 app 仓库分别建仓库)。

## 3. Manifest 仓库规范(`west.yml`)

### 3.1 文件位置

`west.yml` 必须位于 manifest 仓库**根目录**,不允许放入子目录或改名(除非有特殊理由并在文档中注明 `--mf` 用法)。

### 3.2 标准模板

```yaml
manifest:
  remotes:
    - name: zephyrproject
      url-base: https://github.com/zephyrproject-rtos
    - name: org                    # 团队自有仓库(应用等);url-base 末尾勿带 /,否则拼出 //
      url-base: https://github.com/<org>

  projects:
    - name: zephyr
      remote: zephyrproject
      revision: v4.2.0            # 【强制】必须是具体 tag,禁止使用分支名(如 main)
      import:
        # 只拉本项目需要的模块,避免全量 HAL,加快 west update
        name-allowlist:
          - cmsis
          - hal_stm32
          # - segger / mcuboot 等按需增补

    # 应用仓库(T3:作为 project 登记,使其 zephyr/module.yml 被 west 发现,
    # 从而暴露仓库根 boards/ 与 dts/bindings/ 给构建系统)。
    - name: <app-repo>             # GitHub 仓库名(可与本地 path 不同)
      remote: org
      revision: main               # 开发期跟踪 main;发版另出 release manifest 锁具体 tag(见 §3.3)
      path: <project>-app          # 本地目录名

    # 如需覆盖某个 import 进来的模块版本(例如对 hal_stm32 做过安全审计,
    # 需要锁定特定 commit),在此显式声明,覆盖 import 的默认版本:
    # - name: hal_stm32
    #   remote: zephyrproject
    #   revision: <审计通过的commit hash>
    #   path: modules/hal/stm32

  self:
    path: <project>-manifest        # 与本仓库实际目录名一致
```

### 3.3 版本锁定规则(强制)

| 规则 | 说明 |
| --- | --- |
| 依赖项 `revision` 必须是 tag 或 commit hash | zephyr、各模块禁止用分支名,保证任何时间拉取结果一致 |
| 应用仓库自身 revision 的双轨 | 开发 manifest 里应用 project 可跟踪 `main`;**发版时另出 release manifest,把应用锁到具体 tag**,与依赖项一同构成可复现快照 |
| 版本升级需走变更评审 | 修改 `west.yml` 视为修改关键设计输入,需 PR + 至少 1 人 review,并触发全量回归测试(Twister) |
| 每次版本升级需记录 Changelog | 在 manifest 仓库的 `CHANGELOG.md` 中记录:升级前后版本号、升级原因、回归测试结果链接 |
| 关键安全模块单独锁定 | `hal_stm32`(直接影响外设行为)等模块若做过额外安全审计,应显式声明覆盖 import 的默认版本,不完全依赖 zephyr 官方 import 链 |
| 日常勿 `west update` 重置应用仓库 | 应用作为 project 登记后,裸 `west update` 会按 manifest revision 重置它;更新依赖时用 `west update --keep-descendants`,或只更新指定依赖项 |

### 3.4 新板卡接入检查项

引入新芯片/新板卡前,确认:

1. `west boards | grep <board_name>` 能搜到目标板,或明确需要走自定义板级支持(见第 5 节)
2. 目标 revision 是否包含该板/该 SoC 的支持(新芯片系列如 STM32H7R/S 是较新加入的,老版本 revision 可能不含)
3. 若板卡为社区/厂商贡献(非 ST 官方 Nucleo/Discovery 一级支持),需在立项评审记录中注明维护活跃度评估结论

## 4. 应用仓库(`<project>-app`)目录规范

应用仓库同时承担**两个角色**,文件按角色分层放置(对齐 Zephyr 官方 `example-application`):

- **可构建的应用**(application):`CMakeLists.txt` / `prj.conf` / `src/`,放 **`app/` 子目录**,是 `west build` 的目标;
- **Zephyr module 根**(module root):自定义 `boards/` / `dts/bindings/` / `drivers/` 等,放**仓库根**,经 `zephyr/module.yml` 暴露给构建系统,对任意应用可见。

```text
<project>-app/                       # 仓库根 = Zephyr module 根 + 项目容器
├── app/                             # ★ 可构建的应用(west build <project>-app/app 的目标)
│   ├── CMakeLists.txt
│   ├── prj.conf                     # 基础功能配置,所有 build variant 共用
│   ├── prj_release.conf             # release 加固覆盖层(关调试日志、启用看门狗等)
│   ├── prj_debug.conf               # debug 覆盖层(可选)
│   ├── VERSION                      # 应用版本(Zephyr 从 APPLICATION_SOURCE_DIR 读,故必须在 app/ 内)
│   ├── boards/<board_name>.conf     # 应用级板级 Kconfig 覆盖(与官方板同名,west 自动加载)
│   ├── dts/<board_name>.overlay     # devicetree overlay(覆盖官方板部分节点)
│   └── src/                         # 应用源码,按模块划分子目录
│       ├── main.c
│       ├── bms_core/
│       ├── can_if/
│       └── safety_monitor/
│
├── zephyr/
│   └── module.yml                   # ★ 声明本仓库为 Zephyr module,暴露下面 boards//dts/bindings
├── boards/                          # 自定义板级支持(module 暴露,全局可见;仅官方无对应板时需要)
│   └── <vendor>/<board_name>/
│       ├── <board_name>.dts
│       ├── <board_name>_defconfig
│       ├── <board_name>.yaml
│       ├── board.cmake
│       └── Kconfig.<board_name>
├── dts/bindings/                    # 自定义 devicetree 绑定(module 暴露)
├── drivers/                         # out-of-tree 驱动(module 暴露,可选)
├── include/                         # 公共头文件
├── lib/                             # 公共库(可选)
├── tests/                           # ztest 单元测试,west twister -T tests 运行
│   └── bms_core/
│       ├── CMakeLists.txt
│       ├── prj.conf
│       ├── testcase.yaml
│       └── src/
│
├── scripts/
│   └── requirements.txt             # Python 工具依赖(经 west packages pip 装,见 §9)
├── strictdoc_config.py              # StrictDoc 项目配置(需求管理,见 §9)
├── CHANGELOG.md
├── doc/                             # 文档
│   ├── requirements/                # 需求:StrictDoc .sdoc(事实源)+ README(写作指南)
│   │   ├── bms.sdoc
│   │   └── README.md
│   ├── design/                      # 设计:.sdoc,parent → 需求 UID
│   │   └── bms_design.sdoc
│   └── development/                 # 开发文档(构建/脚手架规范等)
├── .clang-format                    # 代码合规规则(见 §6.1)
├── .checkpatch.conf
├── .gitmessage                      # Conventional Commits 提交模板(见 §7.2)
├── .gitignore
├── .vscode/                         # IDE 任务与调试配置
├── .claude/                         # Claude Code 工作流配置(settings / skills / agents)
├── LICENSE
└── CLAUDE.md
```

> 应用版本 `VERSION` 在 `app/` 内(见上,Zephyr 从 `APPLICATION_SOURCE_DIR` 读取);
> `CHANGELOG.md` 是仓库级人读文档,放仓库根。
>
> `boards/` `dts/bindings/` `drivers/` 之所以放**仓库根而非 `app/` 内**:Zephyr 只从「模块搜索根」发现这些资产,而模块根即仓库根(由 `zephyr/module.yml` 声明)。放进 `app/` 里 Zephyr 不会扫描到。当前无自定义板时,`boards/`、`dts/bindings/` 可留空占位(`.gitkeep`),有内容即自动生效。

### 4.1 配置分层原则

配置文件均位于 `app/` 内:

- `app/prj.conf`:只放跨板卡、跨环境都成立的基础功能配置
- `app/boards/<board_name>.conf`:板级差异化配置,west build 时按板名自动加载,不需要显式指定
- `app/prj_release.conf` / `app/prj_debug.conf`:通过 `-DEXTRA_CONF_FILE=` 显式指定,控制 release/debug 差异(日志级别、断言开关、看门狗等)

禁止在 `prj.conf` 里堆砌板级特化配置,后续切换板卡/多板卡并行开发时会难以维护。

### 4.2 CMakeLists.txt 最小模板

位于 `app/CMakeLists.txt`(构建命令:`west build -b <board> <project>-app/app -d build`):

```cmake
cmake_minimum_required(VERSION 3.20.0)
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(<project_name>)

# 源码少时直接列举;模块化后可 add_subdirectory(src) 并在各子目录内 target_sources
target_sources(app PRIVATE src/main.c)
```

## 5. 自定义板级支持规范

仅当 `west boards` 搜不到目标板卡时才需要。步骤:

1. 找一块外设/内核架构最接近的官方板作为模板复制(优先选同一 SoC 系列、同 Cortex 核心的板)
2. 修改 `<board>.dts`:引脚复用、时钟树、外设节点
3. 修改 `<board>_defconfig`:SOC 系列/型号相关 Kconfig
4. 修改 `board.cmake`:指定 flash/debug runner(OpenOCD / J-Link / STM32CubeProgrammer)
5. 新增板级支持必须在 `doc/` 下补充板级说明文档,至少包含:引脚分配表、时钟配置、已验证外设清单、已知限制

## 6. 测试与静态分析挂载点

| 阶段 | 工具 | 挂载位置 |
| --- | --- | --- |
| 单元测试 | ztest + fff.h mock | `tests/<module>/`,通过 `west twister -T tests` 运行 |
| 覆盖率(ASIL D 要求 MC/DC) | Twister v2 内建覆盖率收集 | CI 流程中对 `tests/` 全量执行并产出覆盖率报表 |
| 代码风格/常见缺陷 | checkpatch.pl / Coccinelle | pre-commit hook 或 CI 第一道 gate |
| MISRA C:2012 合规 | Parasoft / Coverity | CI 中作为 merge gate,不通过禁止合入 |
| 原生仿真快速验证 | `native_sim` 平台 | 无硬件时先在 `native_sim` 跑通逻辑,再上板 |

> **边界**:本表工具管**代码质量**(风格、缺陷、MISRA、覆盖率);**追溯**(需求↔设计↔码↔测试)由 StrictDoc 负责,见 §9。二者互补——StrictDoc 的覆盖率指"需求是否被实现/被测试覆盖",与 Twister 的**代码行覆盖率**不是一回事,勿混。

### 6.1 阶段1:C 代码风格合规(已落地基线)

沿用 Zephyr 质量控制体系的第一步:零新增工具,直接复用上游 checkpatch / clang-format 规则,把 app 仓库当作被检查对象挂到 zephyr 现成脚本上。

#### ① 规则文件(置于 app 仓库根目录)

| 文件 | 来源 | 说明 |
| --- | --- | --- |
| `.clang-format` | 从 zephyr 原样拷贝 | clang-format 从被检查文件所在目录逐级向上查找配置,放仓库根即被整棵树(含 `tests/`)继承 |
| `.checkpatch.conf` | 从 zephyr 拷贝并改造 | 已移除上游 `--typedefsfile=scripts/checkpatch/typedefsfile`(该相对路径在 app 仓库不存在);checkpatch 只在当前工作目录查找此文件,故必须置于仓库根 |

> 两文件都放**仓库根**是刻意为之:clang-format 靠"逐级向上查找"、checkpatch 靠"当前工作目录",仓库根是唯一同时满足二者、且被整棵源码树继承的位置。将来新增 `tests/` 无需额外配置即自动覆盖;仅当需要给测试代码放宽规则时,才在 `tests/` 内放叠加用的 `.clang-format`(`InheritParentConfig: true`),checkpatch 的差异化则走 CI 过滤而非嵌套配置文件。

#### ② 检查入口(复用 zephyr 脚本)

checkpatch.pl 本体与 check_compliance.py 均来自 zephyr(`$ZEPHYR_BASE/scripts/...`),app 仓库只提供规则文件。对本分支相对 main 的改动运行:

```bash
# 在 app 仓库根目录执行;check_compliance.py 据自身路径自动推出 ZEPHYR_BASE
python3 $ZEPHYR_BASE/scripts/ci/check_compliance.py -m Checkpatch -m ClangFormat -c main..HEAD
```

#### ③ VS Code Task

`.vscode/tasks.json` 已增加 `Compliance Check (app)`,与 `West Build` 并列,封装上述命令(范围 `main..HEAD`,与 CI 的 PR-vs-main 语义一致)。

#### ④ 环境前置

`ClangFormat` 检查依赖 `clang-format` 与 `clang-format-diff.py`;安装及 Ubuntu 打包差异的软链处理见 `构建指南.md` §2.1。

#### ⑤ 产物忽略

`compliance.xml`(check_compliance 的 JUnit 输出)已加入 app 仓库 `.gitignore`。

> 定位提醒:checkpatch 是"日常风格底线",与 MISRA C:2012 并非一一对应。功能安全认证的 MISRA 证据应以专用工具(Parasoft / Coverity,见上表)为准,不能用 checkpatch 替代。

## 7. 分支与提交规范(配合可追溯性要求)

### 7.1 分支与主干保护

- manifest 仓库、app 仓库均采用主干保护(`main`/`master` 禁止直接 push),一律经 PR 合入
- 分支命名与提交 type 呼应:功能用 `feat/<简述>`,修复用 `fix/<简述>`

### 7.2 提交消息规范(Conventional Commits)

采用 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/zh-hans/)。格式:

```text
<type>(<scope>): <subject>

<body>

<footer>
```

type(必填)取值与其对语义化版本的影响:

| type | 用途 | 影响 SemVer |
| --- | --- | --- |
| `feat` | 新功能 | MINOR |
| `fix` | 缺陷修复 | PATCH |
| `perf` | 性能优化 | PATCH |
| `docs` | 仅文档 | 无 |
| `test` | 测试增改 | 无 |
| `build` | 构建/依赖(CMake、west.yml、SDK) | 无 |
| `ci` | CI 配置 | 无 |
| `refactor` | 重构(不改外部行为) | 无 |
| `style` | 格式(不改逻辑) | 无 |
| `chore` | 杂项 | 无 |

其余字段规则:

- scope(建议):对应 `src/` 模块或子系统,如 `bms_core` / `can_if` / `safety_monitor` / `board` / `manifest`
- subject(必填):祈使句、结尾不加句号,尽量 ≤ 50 字符
- body(可选):说明「为什么」与「做了什么」,每行 ≤ 72 字符
- 不兼容变更:type/scope 后加 `!`,或 footer 写 `BREAKING CHANGE: <说明>`,触发 MAJOR

footer 的可追溯性(强制):

- 涉及 `west.yml` 版本升级、板级支持新增等关键设计输入的提交,footer 必须注明需求编号,如 `Refs: ENV-REQ-BMSCORE-001`
- 关联 issue 用 `Closes #<n>`

示例:

```text
feat(safety_monitor): 增加过压断充保护

当任一电芯电压超过阈值时断开充电回路,响应时限 <10ms。

Refs: ENV-REQ-SAFETY-003
```

本仓库提供 `.gitmessage` 提交模板,首次克隆后执行一次即可让 `git commit` 自动带出模板:

```bash
git config commit.template .gitmessage
```

### 7.3 与 check_compliance 的关系(须知)

`check_compliance.py` 的 GitLint 检查默认按 **Zephyr 上游**规范(`area: summary` + 强制 `Signed-off-by`)校验,与本项目选定的 Conventional Commits 不一致。因此二者取一,避免互斥:

- CI 合规检查**不纳入 GitLint 项**(`check_compliance.py -e GitLint`),提交格式改由 commitlint 校验;
- 或为 GitLint 另行提供一套 Conventional Commits 规则集。

### 7.4 release 可追溯

- 每个 release tag 需能一一对应到:锁定的 west.yml 版本组合 + 通过的 Twister 测试报告 + MISRA 扫描报告,三者可追溯关联
- 版本号与 `app/VERSION`、`CHANGELOG.md` 保持一致;提交里的 `feat` / `fix` / `BREAKING CHANGE` 直接决定 SemVer 递增

## 8. 新项目初始化 Checklist

```text
[ ] 创建独立 manifest 仓库(T3),写入 west.yml,依赖项锁定具体 revision(禁止 main)
[ ] west init -l <manifest-repo> && west update
[ ] west boards 确认目标板存在,或规划自定义板级支持工作量
[ ] west sdk install,确认 scripts/requirements.txt 依赖装齐
[ ] 创建 app 仓库,按第4节目录结构初始化骨架(应用置于 app/,module 资产置于仓库根)
[ ] app 仓库加 zephyr/module.yml,并在 west.yml 登记为 project(暴露自定义 boards/dts)
[ ] 配置 app/prj.conf / app/boards/<board>.conf 分层
[ ] tests/ 下建至少1个 ztest 用例跑通,验证 Twister 集成
[ ] 拷入 .clang-format / .checkpatch.conf 到 app 仓库根,加 Compliance Check task(阶段1,见 §6.1)
[ ] git config commit.template .gitmessage(启用 Conventional Commits 模板,见 §7.2)
```

## 9. 需求管理(StrictDoc)

用 **StrictDoc**(文本 `.sdoc`、git 原生、Python 实现)做需求管理,作为贯穿生命周期的**追溯主干**:需求 → 设计 → 编码 → 测试。

### 9.1 依赖安装(经 west 体系)

StrictDoc 等 Python 工具依赖**不进 `west.yml`**(manifest 只管 git 仓库),而是:

- `bms-app/zephyr/module.yml` 顶层声明 `package-managers.pip.requirement-files: [scripts/requirements.txt]`(路径相对仓库根);
- `bms-app/scripts/requirements.txt` 锁定版本,如 `strictdoc==0.27.0`;
- 安装:`west packages pip --install`(它聚合 Zephyr + 各 module 的 requirements)。

> 这是通用机制:凡是应用侧 Python 工具依赖,都经此声明与安装,统一、可复现、随 app 仓库版本管理。

### 9.2 工程结构

| 载体 | 位置 | 说明 |
| --- | --- | --- |
| 项目配置 | `strictdoc_config.py` | 项目标题、启用特性、文档/源码扫描路径(0.27 起废弃 `.toml`) |
| 需求 | `doc/requirements/*.sdoc` | 自定义 grammar(UID/TITLE/STATEMENT/RATIONALE/ASIL/VERIFICATION_METHOD/STATUS) |
| 设计 | `doc/design/*.sdoc` | `RELATIONS: - TYPE: Parent / VALUE: <需求UID>` |
| 写作指南 | `doc/requirements/README.md` | EARS 句式 + grammar 字段说明 |

### 9.3 全链追溯

| 阶段 | 追溯方式 |
| --- | --- |
| 设计 → 需求 | 设计 `.sdoc` 的 `Parent` 关系指向需求 UID |
| 代码/测试 → 需求 | 源码注释标记 `@relation(<需求UID>, scope=file\|function\|class\|range)`;扫描路径见 `strictdoc_config.py` 的 `include_source_paths` |

生成:`strictdoc export . --output-dir output`(或 VS Code task「StrictDoc Export」),产出 HTML + 追溯矩阵;本地编辑用 `strictdoc server .`。

### 9.4 门禁挂载(随 CI 阶段落地)

当前 CI 未搭建,以下为**规格**,待 CI 阶段接入:

| 门禁 | 触发 | 校验 |
| --- | --- | --- |
| MR 门禁 | PR | `strictdoc export` 校验(UID 唯一、无断链)+ 覆盖率不回退;与 check_compliance 并列 |
| 版本门禁 | `app/VERSION` 递增 | 需求 STATUS 全部已评审;CHANGELOG 已更新 |
| 发布门禁 | release tag | 归档追溯矩阵 + 覆盖率报告(HTML/ReqIF)作 ISO 26262 证据 |
